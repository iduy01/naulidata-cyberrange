# Code Repository

Practical assessment — **PT Nauli Mula Data, Cybersecurity Engineer (Lab & Range Developer)**
Scenario: *"Cookies Reuse & MFA Bypass"* (Red vs. Blue cyber range).

The repository is organised so each item requested in the submission form maps
to exactly one top-level folder.

---

## 1. All application source code (Node.js) → `application/`

```
application/
├── app/
│   ├── server.js        # the vulnerable application ("Admin Feedback System", Express)
│   │                    #   - SCENARIO75{...} flag constants
│   │                    #   - rudimentary WAF (WAF_RULES: blocks <script>, document, cookie, onerror)
│   │                    #   - in-memory validSessions set  (the flawed bearer-token store)
│   │                    #   - routes: GET /, POST /api/feedback, GET+POST /login,
│   │                    #            GET+POST /api/verify-mfa, GET /dashboard, /logout,
│   │                    #            /robots.txt, /healthz
│   └── package.json     # express, cookie-parser
└── bot/
    ├── bot.js           # simulated administrator (Puppeteer / headless Chromium):
    │                    #   signs in (user + password + MFA) and loops on /dashboard
    │                    #   so a stored XSS payload executes in an authenticated session.
    │                    #   Includes the re-auth guard that survives an app restart.
    └── package.json     # puppeteer
```

## 2. Docker / Docker Compose files → `docker/`

```
docker/
├── docker-compose.yml   # the whole lab (3 services)
│                        #   app  -> host :3075   (vulnerable Node.js app)
│                        #   bot  -> internal only (headless admin)
│                        #   sshd -> host :2275   (Blue Team SSH, analyst / blue_team_rocks)
│                        # shared volume ../logs -> /opt/admin/logs (read over SSH by the Blue Team)
├── app.Dockerfile       # builds the application image (node:20-alpine + python3 for the log seeder)
└── bot.Dockerfile       # builds the bot image (node:20-slim + Chromium + puppeteer deps)
```

Because the compose file lives in `docker/`, always invoke it explicitly:

```bash
docker compose -f docker/docker-compose.yml up -d --build
```

The Blue Team SSH user is created **declaratively** through the compose environment
(no separate `useradd` script needed):

```yaml
- USER_NAME=analyst
- USER_PASSWORD=blue_team_rocks
- PASSWORD_ACCESS=true
- SUDO_ACCESS=false
```

## 3. Setup scripts (Bash, Python) — provision VM, create SSH user, generate/inject mock logs → `scripts/`

```
scripts/
├── provision.sh         # one-shot provisioning of the Proxmox guest (run as root,
│                        #   Debian 12 / Ubuntu 22.04-24.04):
│                        #    1. install Docker Engine + compose plugin
│                        #    2. create /opt/admin/logs
│                        #    3. add the internal DNS entry feedback.admin.local
│                        #    4. docker compose up -d --build   (this also creates the SSH user)
│                        #    5. seed the mock telemetry via inject_logs.py
├── inject_logs.py       # generates + injects the mock telemetry into /opt/admin/logs:
│                        #   access.log (Nginx-style combined + X-Forwarded-For) and
│                        #   error.log  (WAF / security warnings). Builds the complete
│                        #   Red-vs-Blue story the Blue Team must reconstruct
│                        #   (attacker 10.10.14.50, baseline 192.168.1.100, the Base64
│                        #   XFF value, the CRITICAL "Authentication bypass anomaly" line).
│                        #   Flags: --dir, --append, --clear
└── verify.sh            # automated self-test, ~20 checks across infra + Red + Blue paths
```
